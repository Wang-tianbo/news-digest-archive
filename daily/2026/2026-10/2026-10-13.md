## AI 研究前沿

### CRBugBench：code review agents 离 lights-off software factory 仍有距离

- 类型：benchmark
- 研究问题：当 agent 生成代码速度超过人类 review 速度时，review agents 是否足以承担“无人值守软件工厂”的 bug 检测。
- 核心思路：论文构建 CRBugBench，从 repository history 中挖掘人类确认过的 bug，并把每个 bug 与引入它的 PR 配对成 review task；数据包含 98 个开源 GitHub 仓库中的 1,000 个任务，以及一家大公司私有仓库中的 800 个任务。
- 为什么可能影响未来：论文报告最佳组合在 top-5 comments 中抓到 71.9% 的 bug，但复杂变更、非局部推理和私有仓库上下文会显著拉低效果。这直接影响 Copilot / Cursor / Claude Code / Codex 这类工具是否能从“写代码”扩展到“可信 review”。
- 局限 / 待验证点：早期 arXiv 论文，本次未复现实验；私有仓库数据不可直接外部复查。
- 研究成熟度：早期 benchmark
- 可复现状态：论文原文公开；本次未验证代码或数据
- 原文链接：[arXiv:2610.13668](https://arxiv.org/abs/2610.13668)
- 权威解读：暂无
- 我的判断：这条给本期产品信号降温：agent review 已经有用，但还不是 lights-off。团队应该按 PR 复杂度分配 review effort，而不是默认自动放行。

### TestSuiteBench：agents 能写应用，但不一定能写强测试

- 类型：benchmark
- 研究问题：coding agents 能否仅根据规范为完整软件应用生成强测试套件，而不只是为单个函数或 bug fix 写测试。
- 核心思路：论文构建 165 个开源应用，每个应用都有结构化行为规范、参考实现、参考测试套件和平均 74 个 mutants，用 mutation score 衡量测试是否真正覆盖行为要求。
- 为什么可能影响未来：论文发现 frontier coding agents 生成的测试大多能在参考实现上通过，但 mutation score 低于 60%；同时，同一规范下生成的实现能通过 82% 参考测试。这说明 agent “能构建”与“能验证”之间存在缺口。
- 局限 / 待验证点：早期论文；benchmark 是否覆盖真实企业测试策略、端到端测试和非功能需求还要继续观察。
- 研究成熟度：早期 benchmark
- 可复现状态：论文原文公开；本次未验证代码或数据
- 原文链接：[arXiv:2610.13065](https://arxiv.org/abs/2610.13065)
- 权威解读：暂无
- 我的判断：这条非常关键。未来 coding-agent 的 merge gate 不能只问“测试是否通过”，还要问“测试是否有能力区分错误实现”。

### Full sandbox snapshots：长程 coding-agent 恢复不只靠 git diff

- 类型：论文
- 研究问题：coding agents 在失败前常常已经改出了有用状态；如果恢复完整开发环境快照，而不是从初始状态重试，是否能提高长程任务完成率。
- 核心思路：论文实现类似 Go-Explore 的 full Daytona snapshot search，发现当进展保存在数据库、服务或其他运行态而非 repo diff 中时，完整环境快照更能提升求解率和效率。
- 为什么可能影响未来：这解释了为什么 agent 产品都在做 worktree、workspace session、hosted runtime、snapshot、replay 和 trajectory。真实任务的状态常常不在 git 里。
- 局限 / 待验证点：早期论文；本次未复现，也未确认不同 sandbox 平台、不同服务栈和真实团队流程中的成本收益。
- 研究成熟度：早期论文
- 可复现状态：论文原文公开；本次未验证代码
- 原文链接：[arXiv:2610.13841](https://arxiv.org/abs/2610.13841)
- 权威解读：暂无
- 我的判断：这条和 Qwen Code / Cursor / Codex 的运行层更新高度相关。长任务 agent 的核心能力之一会是“保存、分叉和回到正确的开发状态”。

### RATED：工具检索开始考虑运行时可靠性，而不只是语义相关

- 类型：论文
- 研究问题：agent 在选择外部工具时，是否应把工具实时可用性纳入检索排序，而不只按语义匹配。
- 核心思路：RATED 用 frozen dual-encoder 做语义匹配，再用 contextual bandit 根据执行反馈重排工具候选；论文还提出 EcoAgent，覆盖 5,172 个真实工具和 210,000+ query-tool pairs。
- 为什么可能影响未来：MCP / plugin / tool ecosystem 越大，工具不可用、API 失败、schema 漂移和权限问题越常见。可靠性-aware retrieval 会影响 agent 平台如何在真实工具池中选工具。
- 局限 / 待验证点：早期论文；本次未复现，也未验证 EcoAgent 与主流 MCP registry 或企业私有工具目录的贴合程度。
- 研究成熟度：早期论文
- 可复现状态：论文称代码和数据可用；本次未验证
- 原文链接：[arXiv:2610.13889](https://arxiv.org/abs/2610.13889)
- 权威解读：暂无
- 我的判断：这条把工具调用从“找到相关工具”推进到“找到现在能可靠执行的工具”，很适合后续观察 MCP 生态。

## AI 外围情报观察

### Agent 安全治理：非预期行动已经是产品和评测共同问题

- 事实：Anthropic 报告披露 Claude 在真实网站、表单、token、短链接和第三方服务上的非预期行为；同一时期，Z Code 3.15.1 增加危险命令确认和内置浏览器站点权限管理，Qwen Code nightly 把 monitor startup failures 作为 tool errors 上报。
- 为什么会反作用于 AI 主线：agent 越能跨工具、跨网站、跨服务执行，安全治理就越不是合规附录，而是产品可用性的前置条件。
- 我的判断：下一阶段 agent 安全竞争会从“安全声明”转向“默认边界”：危险动作是否确认、站点权限是否显式、工具错误是否进入执行语义、评测是否禁用或隔离 live internet。
- 来源：[Anthropic Research](https://www.anthropic.com/research/investigating-unintended-model-actions)、[Z Code changelog](https://zcode.z.ai/en/changelog)、[Qwen Code release](https://github.com/QwenLM/qwen-code/releases/tag/v0.25.1-nightly.20261012.18f80f5666)

## 值得继续跟踪

- 豆包 2.0 / Doubao-Seed-2.0-Code 在火山方舟 API、TRAE 和第三方 agent 工具中的真实可用性、价格和稳定性。
- Z Code GLM HighSpeed 是否从灰度体验进入正式模型选择，并公开更多延迟、上下文、成本和质量信息。
- Qwen Code managed-agent mailbox、worktree child-run settlement、test failure explorer 是否进入稳定版。
- Copilot repository instructions / skills / agents / MCP 是否成为跨 repo、cloud agent 和 PR review 的事实标准。
- CRBugBench、TestSuiteBench、sandbox snapshot 和 RATED 是否被主流 coding-agent 产品或评测榜单采用。

## 判断变化

- 延续了什么：AI 编程代理继续围绕运行层、项目上下文、MCP / tool 边界、workflow replay 和企业协作入口推进。
- 新出现了什么：本期中国侧信号更强，豆包 2.0、Z Code 3.15.1、Qwen Code nightly 同时指向 Code 模型、子 agent 编排和 agent 安全边界。
- 被削弱了什么：单点速度、单次 demo 和 headline 榜单不足以判断 agent 竞争力；review、测试、恢复和工具可靠性正在成为更硬的衡量维度。
