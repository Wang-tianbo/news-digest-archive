# 长期议题台账说明

长期议题台账是这个仓库里非常关键的一层。

如果说：

- 日报在记录“今天发生了什么”
- 周报在判断“这一周哪些趋势在重复出现”
- 月报在总结“这个阶段的格局发生了什么变化”

那么议题台账记录的是：

- 哪些问题值得持续追踪 1 个月、1 个季度，甚至 1 年
- 哪些判断随着新事实进入，需要被强化、修正或拆分

## 为什么需要它

没有议题台账时，日报和周报很容易停留在“写得很好”，但长期上仍然是按天散落的。

有了台账之后，你会开始积累真正可复用的认知对象，例如：

- `agent_api`
- `runtime_governance`
- `mobile_agent_handoff`
- `team_level_metrics`
- `china_open_agent_runtime`

这些对象会跨越很多篇日报和多期周报，被持续更新，而不是每次从头解释一遍。

## 台账的使用原则

### 1. 不要开太多议题

议题台账不是把每条新闻都建一个页面。

只有满足下面至少两个条件时，才建议新建议题：

- 在多篇日报里重复出现
- 涉及多家公司或多产品
- 会影响未来 1 个月以上的判断
- 已经不是单点事件，而是方法、格局或工作流变化

### 2. 优先跟踪“问题”，而不是“新闻”

好的议题通常像问题：

- 编程代理是否正在 API 化
- 运行时治理是否会成为 agent 产品的主战场
- 中国公司是否会率先把公开 agent runtime 做成熟

而不是：

- 某个公司发了某个版本

### 3. 每次更新都要写“判断变化”

台账的核心不是事实列表，而是：

- 这个议题比上次更强了还是更弱了
- 为什么
- 下一次观察要看什么

## 建议工作流

推荐这样使用这套仓库：

1. 日报里用元数据记录 `themes`、`signals`、`followups`
2. 周报里把重复出现的主题整理成“本周议题台账”
3. 当某个主题连续 2 周以上都值得写，就正式升格为长期议题台账
4. 月报回看这些议题，看哪些已经进入阶段性格局，哪些已经转弱
5. 年报只保留那些全年都反复被验证的长期主线

## 推荐状态

- `rising`
  议题正在快速升温，信号明显增强
- `ongoing`
  议题持续存在，仍是重要主线
- `stabilizing`
  议题已经从新趋势变成稳定现实
- `weakening`
  议题热度或重要性正在下降
- `watch`
  议题值得关注，但证据仍然不够强

## 文件建议

推荐把正式议题台账放在未来的 `ledgers/` 目录下，例如：

- `ledgers/agent-api.md`
- `ledgers/runtime-governance.md`
- `ledgers/mobile-agent-handoff.md`

当前仓库先提供模板和方法，不强制立即建目录。等第一批议题稳定后，再正式把 `ledgers/` 纳入仓库结构。
