## 今日评论与判断

基于本期确认事实样本，我的判断是：今天的主线不是“谁又发了更强模型”，而是“强模型进入真实工作流后，运行时系统开始补账”。Codex 的网络审批并发硬化、Qwen Code 的 CI 证据 / approval 外移、Pydantic AI 的 provider / tool-call ID 规范化、Ollama 的本地模型适配，都是 agent 走向长任务和组织使用时必须补的底座。

第二个判断是，桌面 agent 会重新成为竞争入口。过去一周的 OpenAI Presence、Qwen Web Shell、LobeHub / Cherry Studio / OpenWorker 都在把 agent 放进本地文件、日历、Slack、Jira、GitHub、知识库和可审批动作里。真正的壁垒不一定是聊天 UI，而是能不能把“读、改、发、跑命令”做成可暂停、可批准、可审计的工作流。

第三个判断是，研究侧也在向同一问题靠拢。OpenForgeRL 关注的不是单个模型能力，而是如何在 Claude Code / Codex 这类复杂 harness 中采集 rollout、训练和评估 agent。未来 agent 能力提升可能越来越依赖真实 harness 与环境，而不是只依赖离线题库。

第四个判断是，Health in ChatGPT 这类垂直场景会把 AI 产品治理推到更硬的位置。健康数据接入、默认权限提示、记忆边界和训练排除都值得记录；但它也意味着产品团队必须承担更高的误用、误导和责任边界压力，不能只用“不是医生替代品”一句话解决。

## AI 研究前沿

### OpenForgeRL：让真实 agent harness 进入 RL 训练回路

- 类型：论文
- 研究问题：Claude Code、Codex、OpenClaw 这类 agent 依赖复杂、多进程、带工具和外部系统的 inference harness，传统 SFT / RL stack 难以直接表达这种 stateful harness inference；如何在真实 harness 与环境中训练和研究 agent。
- 核心思路：论文 [OpenForgeRL: Train Harness-native Agents in Any Environment](http://arxiv.org/abs/2607.21557v1) 提出用轻量 proxy 接管 harness 的模型调用并记录为训练数据，再用 Kubernetes orchestrator 为每个 rollout 启动独立远程容器，从而把 harness 推理和标准 RL 代码库解耦。
- 为什么可能影响未来：如果 agent 的能力越来越依赖真实 IDE、terminal、browser、MCP、GUI 和多工具环境，那么训练与评测必须靠近这些 harness。OpenForgeRL 的价值在于把“agent 用什么环境工作”也纳入训练闭环。
- 局限 / 待验证点：本期仅确认论文与摘要，未验证代码、数据、复现实验或成本；Kubernetes rollout 的工程复杂度和安全隔离也需要进一步验证。
- 研究成熟度：早期论文 / framework 设计。
- 可复现状态：本期未验证；是否有完整可运行代码和第三方复现待查。
- 原文链接：[arXiv:2607.21557](http://arxiv.org/abs/2607.21557v1)
- 权威解读：暂无；本期仅用论文原文。
- 我的判断：它值得跟踪，因为它把 agent 训练从离线题库推向“真实 harness + 真实环境 + 可记录 rollout”，与今天 Codex / Qwen Code / Claude Code 的 runtime 主题高度一致。
